# Configuration reference

All operational values are edited in Settings, validated by Pydantic and versioned in SQLite. The canonical schema is returned by `GET /api/settings`; unknown fields, non-finite numbers and invalid ranges are rejected. The initial JSON template is generated by `python -m trader init`. Environment variables configure credentials and the database path, not hidden risk overrides.

Fractions are decimals: `0.25` means 25%. Money is USD. Live is disabled and automation stopped initially. Presets are design assumptions, not empirically optimal settings.

## Broker

| Parameter | Default | Meaning |
|---|---|---|
| `broker` | `local` | local / alpaca / ibkr. Local requires simulation. |
| `mode` | `simulation` | simulation / paper / live; mode separation is mandatory. |
| `account` | `` | Exact external account ID; optional local ledger name. Switching isolates ownership and history. |
| `dedicated_account` | `False` | Required externally. Shared accounts fail closed. |

## Capital

| Parameter | Default | Meaning |
|---|---|---|
| `allocated` | `500` | Bot budget cap. Local changes add/withdraw virtual cash as explicit flows. Cannot withdraw invested cash. External changes verify available cash. |

| `equity_percent` | `0.25` | Account equity fraction at initial binding. |

| `cash_reserve` | `0.2` | Minimum cash fraction. Effective deployment is min(deployment,1-reserve). |
| `reinvest_profits` | `True` | If false, sizing base is capped at contributed capital. Losses always reduce available capital. |
| `include_deposits` | `False` | External true is rejected: reliable cash-flow integration is unfinished. Explicit budget adjustments are supported. |
| `fractional` | `True` | Only if instrument and adapter permit. IBKR adapter is whole-share only. |
| `min_order` | `1` | Minimum order notional in USD, $1 default. |

## Application state and controls

Start/resume sets persistent automation active. Pause keeps protective monitoring/reconciliation active and leaves broker orders open. Stop disables scheduler work. Kill blocks all new submissions but cannot recall an order already in flight. Cancel acts only on known bot orders; unknown orders cause an ownership halt. Emergency liquidation requires an explicit phrase and works within order limits. Pending/ambiguous submissions block further planning. Interrupted cycles are not blindly replayed.

Broker/account/capital/strategy changes stop automation and revoke live activation. Risk-only changes apply under the same mutation lock at the next validation; reductions are immediate when the next cycle can execute. Settings cannot retroactively cancel filled orders or eliminate market gaps. Changes to critical configuration are rejected while orders remain pending.

`TRADER_DB` selects SQLite state (default runtime/trader.db). `.env.example` lists optional credentials. Fixed starting defaults cannot silently consume cash deposited outside the ledger. Dedicated broker accounts must start without holdings/orders. Restoring a database resets activation, stops automation and enables kill.

## Strategy adjustments and data limitations

The bridge corrects upstream ranker lookback from top_n_per_group to configured zscore_window, feeds completed weekly data to slow signals and actual daily data to fast-risk-off. The upstream exception-persistence singleton-history TODO remains; historical persistence triggers cannot be claimed. Centralized operational stops act on persisted holdings, independently of upstream stops. See IMPLEMENTATION_PLAN.md.

Backtests use an unchanged present-day user universe, adjusted historical prices and estimated costs. They do not claim a survivorship-free institutional data set. OOS boundary reporting does not prove that a user has never tuned parameters to that interval. Benchmark comparisons are initially fully invested and can differ in cash exposure from risk-constrained strategies.

## Intraday research settings

The optional lab uses a separate `intraday_settings` SQLite state key, not deployed trading settings. Validated fields: symbol (supported dataset), strategy (momentum/reversion/cash/hold), capital >0, allocation (0,0.8], lookback 4–256 bars, threshold >0, stop_loss and max_drawdown fractions (0,1), fees/adverse execution 0–100 bps per side, maximum daily entries 1–30. Quote friction is an assumption, not measured historical spread. Exit orders may exceed the entry limit for protection. Hold benchmarks bypass stops/drawdown and liquidate only at the end. All quantities pass through Nautilus instrument precision; current equity research is whole shares only.

The API is `/api/intraday/settings` GET/PUT, `/api/intraday/backtest` POST and `/api/intraday/runs` GET. Mutation requests require the existing local-origin guard and X-Trader-Intent: console. Research results are isolated from real trading performance.

## ML and persistent intraday sessions

`interval`: 5 or 15; `strategy`: also accepts `ml`; `model_id`: locally trained version identifier; `ml_buffer`: extra expected-return margin above round-trip modeled costs (default 0.001). Maximum daily loss defaults to 5%, peak drawdown 15%, initial-capital loss 20%. The same portfolio-loss function governs swing/intraday engines. Hold benchmarks intentionally bypass loss stops for comparison.

Training families are `forest` and `boosted`, with horizon 8 or 16 bars. Features lag one bar and labels mature strictly before the UTC cutoff. Evaluation before cutoff is rejected. Model files must match their saved SHA-256. Only local generated artifacts are loaded; never replace these with untrusted pickle/joblib files.

Continuous sessions use immutable saved settings and isolated virtual cash. To change model or risk settings, stop the session and create a new one. Only one virtual intraday session can run at a time. SQLite stores session state, atomic cycle checkpoints and stable fill identities. T+1 uses the next NYSE session, withholding only unsettled sell proceeds; new positions may use other settled cash. Crypto cash settles immediately in the model.

Endpoints: `/api/intraday/models/train`, `/models`, `/sessions`, `/sessions/{id}` and POST `/sessions/{id}/{start|pause|resume|stop|step|liquidate}` under the same intraday prefix. The scheduler advances up to 16 bars per ten-second tick; actual timing depends on reconstruction time. Replay reconstruction trades speed for deterministic restart safety; long histories can become slow. It never resubmits orders to an external broker.

## Growth policy defaults

Separate `GrowthConfig`: $500 virtual capital; 60% maximum deployment; 30% per BTC/ETH asset; 40% reserve; estimated stop risk 0.5% equity per entry; 2% daily entry pause; 8% peak drawdown liquidation/halt; 10% research drawdown tolerance. Bounds permit reducing these risk exposures, not increasing them beyond the agreed budget. Fees are explicitly estimated until account-specific fees are verified.

`/api/growth/research` returns the recorded protocol, trials, version manifests and results. `/api/growth/forward` returns forward status; POST `/forward/configure` accepts `{config: GrowthConfig, models: {symbol: model_id}}`; POST `/forward/start` or `/forward/stop` controls public observation. Model selection is rejected unless historical qualification passes. Configuration freezes after the first observation, and records are not reset to hide losses. All endpoints use the existing local-origin and intent guards.

Forward storage uses additive SQLite tables `growth_forward`, `growth_observations` and `growth_fills`. Existing tables and histories are unchanged. Back up the database, runtime growth-model directory and market-data snapshots together. Execution is reconstructed deterministically from the observation log; long histories take more time. Quote sampling and protective decisions are hourly, so intrahour losses and gaps are not capped by modeled stops. Failed data collection stops observation until explicitly restarted.

A subsequently qualified version can be supplied through POST `/api/growth/forward/models` with `{symbol: model_id}`. Promotion validates the historical qualification gate, instrument and model age; it logs a decision-time change without resetting equity or old observations. Removing all model entries returns future decisions to cash; existing positions still follow their original expiry/stops. Model training/validation must be refreshed monthly; an overdue version stops simulation rather than being promoted automatically. No manual weekly income target changes sizing.

## Long-history regime research configuration

This configuration is a locked research protocol, not an operational settings
page or a live strategy. `trader/growth/regime.py` defines eight base variants:
20/100 or 50/200 completed-daily moving averages, 24- or 72-hour momentum from
completed four-hour bars, and the 80th or 90th percentile rolling volatility
ceiling. The ML entry filter has two fixed families (`boosted`, `forest`) and two
probability thresholds (`0.55`, `0.60`). It never overrides a base-regime exit.

The portfolio uses `GrowthConfig`: $500 initial capital, 60% maximum deployment,
30% per asset, 40% reserve, 0.5% estimated risk per entry, 2% daily-loss entry
pause, and 8% drawdown halt. Base costs are 10 bp fees plus 5 bp adverse
execution per side. These values are explicit assumptions and are evaluated at
1.5x and 2x; they are not editable evidence of an account tariff.

`GET /api/growth/regime` returns the protocol, locked selection, and summary.
There is deliberately no endpoint to promote this experiment: the base rule and
ML filter both failed the 2022 selection gate. `historical_qualified` and
`live_qualified` remain false. Protective-stop exits require the base regime to
reset before another entry, preventing immediate stop/re-entry churn.

## Defensive trend research configuration

`trader/growth/defensive.py` implements the selected research rule. Its fixed
parameters are a 100-day BTC trend, 90-day BTC momentum, Monday 00:00 UTC
rebalance, 10% maximum allocation per asset, 20% maximum total deployment, 80%
minimum cash, and a 30% annualized volatility target. Features use the previous
completed daily close and orders use the following daily open. Fractional
quantities and 15 bp adverse cost per traded notional are modeled; evaluation
also runs at 30 bp.

The evaluator searches 81 combinations of lookback, momentum, cadence and
allocation mode while keeping the conservative risk limits fixed. Selection
uses 2019–2021 development and 2022–2023 validation only. Run
`python -m scripts.evaluate_defensive_trend`; artifacts are written under
`research/defensive_trend/`, and `GET /api/growth/defensive` exposes the locked
protocol, selection and summary to the local dashboard.

These are research constants rather than active broker settings. There is no
promotion or execution endpoint for this candidate. Historical profitability
does not bypass the prospective paper, verified-cost and execution-readiness
requirements.

## Drawdown frontier research configuration

`DefensiveRisk` makes the research exposure limits explicit without changing
active broker settings. The 20% diagnostic tier uses 20% per-asset and 40%
total-deployment caps; the 50% tier uses 50% per-asset and 100% total-deployment
caps. Both retain the 30% annualized volatility target, long-only behavior and
15 bp base / 30 bp stress transaction-cost assumptions.

Run `python -m scripts.evaluate_drawdown_frontier`. The script selects each tier
from the same 81 trend configurations using development and validation periods,
then evaluates the already-inspected later period. Results are available at
`GET /api/growth/drawdown-frontier`. These drawdown values are evaluation
budgets, not guaranteed stop levels. Neither tier has a promotion endpoint.

## Hedge research configuration

`trader/growth/hedges.py` contains three isolated research engines. None is
connected to broker routing.

- The BTC short overlay tests 100/150/200-day trend, 30/90/180-day momentum,
  three negative-regime triggers and hedge fractions of 25%, 50% or 100% of the
  tier exposure. Shorts cost 10% annualized plus 15 bp trading friction; stress
  uses 20% carry and 30 bp friction.
- Market-neutral relative value tests 30/60/120/180-day BTC/ETH ratio windows,
  1.0/1.5/2.0 entry z-scores, 0/0.5 exits, daily/weekly cadence, and 20%/30%
  volatility targets. Long and short legs have equal target notional.
- Protective puts test 5%/10%/15% out-of-the-money strikes, 50%/100% coverage,
  28/56-day tenor, and nine slow trend/momentum combinations. Weekly marks use
  Black-Scholes, lagged 30-day realized volatility and a 25% volatility markup.
  Stress raises modeled volatility another 25% and doubles trading friction.

Research endpoints are read-only at `GET /api/growth/hedges`. A local result
cannot enable shorting, margin, derivatives or options. Those instruments would
require a separately implemented and verified broker capability, margin model,
funding/borrow reconciliation, liquidation controls and bot-ownership ledger.
